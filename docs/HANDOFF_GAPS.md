# 핸드오프 문서만으로 판단할 수 없었던 점

세션 2에서 기존 `HANDOFF.md`를 읽고 이어받으며 문서만으로는 확정할 수 없던 점과, 그때 내린 판단을 기록한다. 다음 세션이나 저장소 소유자가 확인해야 할 항목이다.

| # | 문서에서 알 수 없었던 점 | 이번 세션의 판단 | 확인 필요 |
|---|---|---|---|
| 1 | "구현 완료"라고 적혀 있었지만 테스트를 한 번도 실행하지 않아 실제 동작 여부를 알 수 없었다. | 직접 실행해 기존 5개 통과를 확인했다. 다만 코드 검토로 Mock 제약을 깰 수 있는 `env={}` 결함 등을 찾았다(HANDOFF.md "진행 상태" 참고). **"완료"는 검증된 상태가 아니었다.** | 앞으로는 HANDOFF에 "실행 확인" 여부를 따로 적을 것 |
| 2 | 작업 대상 브랜치와 병합 계획. 로컬은 `retest-a`인데 workflow는 기본 브랜치를 checkout한다. `retest-a`가 원격에 push되었는지도 문서에 없었다. | `retest-a`에서 작업했고 병합은 하지 않았다. 이번 세션은 GitHub에 연결되지 않아 원격 상태를 확인하지 못했다. | `retest-a` → `main` 병합 여부와 시점 |
| 3 | 스냅샷의 "불변성". 코드 docstring에는 immutable이라고 되어 있었지만, 실제로는 재실행 때 덮어썼다. 어느 쪽이 의도인지 문서에 없었다. | 마감값은 보존하는 것이 맞다고 보고 기존 파일을 유지하도록 했다. `--force`로만 덮어쓴다. | 재실행 때 덮어쓰기를 원한다면 기본값 변경 |
| 4 | "마감" 시각의 정의. GitHub cron은 지연될 수 있어서, 00:05 KST 실행이 늦어지면 자정 이후 수집된 차트가 전날 마감으로 저장될 수 있다. | 실행 시점의 최신 차트를 마감으로 쓰고, 원본 수집 시각(`source_updated_at`)을 함께 기록해 사후 확인이 가능하게 했다. 제약 때문에 `update_chart_data.py`의 수집 방식은 바꾸지 않았다. | 엄격한 23:59 마감이 필요하면 별도 설계 필요 |
| 5 | 실행이 빠진 날의 비교 기준. | "전일"이 없으면 더 앞선 가장 최근 스냅샷과 비교하고, `compared_to`와 카드에 기준 날짜를 표시한다. | 이 경우 비교를 생략하는 편을 원하는지 |
| 6 | "여러 LLM"이 서로 다른 제공자나 모델을 의미하는지. 기존 문서에는 세 역할 모두 기본값 `gpt-4o-mini`로 적혀 있었다. | 역할별 URL·모델·키를 분리한 구조는 유지했다. 실제 제공자 선택은 Variables 설정에 맡겼다. | 역할별로 쓸 실제 제공자와 모델 |
| 7 | 이전 세션의 커밋 메시지에 "Codex/Luna"가 들어 있어 다른 도구가 작성한 것으로 보인다. 당시 확인 명령(`git diff --check` 등)의 결과는 기록되어 있지 않았다. | 같은 확인을 작업 공간 사본에서 다시 했다(JS 문법, 테스트, 제약 파일 해시). 이번 세션에는 사용자 PC의 셸 접근이 없어 `git` 명령 자체는 실행하지 못했다. | 사용자 PC에서 HANDOFF.md의 확인 명령 실행 |
